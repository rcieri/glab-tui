# AI Agent Instructions for `glab-tui`

Welcome, AI Agent! This document contains essential context, architectural guidelines, and coding standards for navigating and contributing to `glab-tui`. Please adhere to these rules when analyzing the codebase, writing new features, or refactoring.

## 1. Project Overview

`glab-tui` is a Terminal User Interface (TUI) for managing GitLab and GitHub repositories. 
Instead of implementing full REST/GraphQL API clients, **`glab-tui` shells out to the official `glab` and `gh` CLIs** under the hood.

* **Primary Language:** Rust (Edition 2024)
* **TUI Framework:** `ratatui` (v0.30.1)
* **Syntax Highlighting:** `syntect` (v5, `parsing` + `regex-fancy` features) running bat's syntax set from `two-face` (v0.5, `syntect-fancy` feature: fancy-regex dump, no C dependency)
* **Word Diff:** `similar` (v3.2, no default features: only its Myers algorithm is called) over `unicode-segmentation` (v1.13, already in the tree through ratatui) word boundaries, for word-level marks inside changed diff lines
* **Markdown Rendering:** `pulldown-cmark` (v0.13.0, GFM tables/code/lists)
* **Async Runtime:** `tokio` (v1.38, full)
* **Async Traits:** `async-trait` (v0.1.92)
* **CLI Parsing:** `clap` (v4, derive)
* **Terminal Handling:** `crossterm` (v0.29)
* **Clipboard:** `arboard` (v3.6)
* **Config/Themes:** `toml` (v1.1) crate; config at `~/.config/glab-tui/config.toml`
* **YAML:** `serde-saphyr` (v1.1, `deserialize` only) — parses `workflow_dispatch` inputs from GitHub workflow files. It replaced the deprecated `serde_yaml`. serde-saphyr 1.2+ needs Rust 1.89, so the MSRV-aware resolver holds it at 1.1.
* **Process & Session Handling:** `libc` (v0.2) — Unix setsid for background commands & signal masking during terminal handoff
* **Package:** `glab-tui-crate` (binary: `glab-tui`)

### Dual-Engine Architecture
The application detects whether the current repository is hosted on GitHub or GitLab and instantiates either a `GlabBackend` or `GhBackend`. Detection is centralized in `git_helpers::detect_backend(remote_url, override_kind)` ([src/git_helpers.rs](src/git_helpers.rs)): `github.com` remotes (with or without `www.` prefix) resolve to GitHub; other hosts are probed with `gh auth status --active --hostname <host>` and `glab auth status --hostname <host>`, defaulting to GitLab when neither/both respond. Without an `origin` remote (e.g. `-r owner/repo` outside a checkout), `git_helpers::detect_backend_without_remote` applies the same rule to `gh auth status --active` / `glab auth status` with no hostname. A repo-local `backend = "github" | "gitlab"` config override always takes precedence — set it for SSH aliases or hosts serving both platforms. Always route backend detection through `detect_backend`; do not reimplement inline `github.com` string matching. Both backends implement the `Backend` trait ([src/backend/mod.rs](src/backend/mod.rs)). The domain layer ([src/domain/](src/domain/)) calls backend methods through `GitlabClient` ([src/domain/client.rs](src/domain/client.rs)). Runtime backend identification is available via the `BackendKind` enum (`BackendKind::GitLab` / `BackendKind::GitHub`) which also provides host-aware terminology through `BackendKind::term()`.

The `namespace/project` context passed as `-R <repo>` to every `glab`/`gh` call is extracted from the remote URL by `git_helpers::parse_project_path` ([src/git_helpers.rs](src/git_helpers.rs)), which keeps every path segment after the host so nested GitLab subgroup namespaces (`group/subgroup/project`) resolve correctly. Always use this helper — do not reimplement remote-URL parsing inline.

Group/org-level browsing is supported via the `Scope` enum ([src/scope.rs](src/scope.rs)) and the `-g`/`--group` CLI flag (`src/cli.rs`). A `Scope::Group` is inferred from the remote URL by `git_helpers::parse_group` (paths without a slash), from the `--group` CLI/`config.group` value, or from `parse_project_path_from_web_url` (web URLs). All listing backend methods (`list_issues`, `list_mrs`, `list_pipelines`, `list_runners`, `list_releases`, `list_milestones`, `list_branches`, `list_environments`, `list_deployments`, `fetch_members`) accept a `&Scope` and use `cli_group_arg()` to inject `-g` (glab) / org flags instead of `-R`. Recent groups are persisted in `recent_groups.json` ([src/utils/cache.rs](src/utils/cache.rs)). In group scope, entity creation and edit forms embed a selectable "Project" field that dynamically fetches project-scoped labels, assignees, and milestones upon selection.

**Group scope on GitLab is partial too.** Issues, MRs, milestones, labels and members aggregate across the group, but `GlabBackend::list_pipelines`, `list_runners`, `list_releases`, `list_branches`, `list_environments` and `list_deployments` return `Err("Group-level … not supported")`, so the Pipelines, Runners, Releases, Branches and Environments (including its deployments) tabs only work in repository scope. On GitHub, only a subset of the GH backend methods support `Scope::Group` (i.e. an org scope); the rest return `Err` and the UI shows an error toast. The currently supported GH backend methods with `Scope::Group` are: `list_issues` (via `search/issues?q=owner:org+is:issue`), `list_mrs` (via `search/issues?q=owner:org+is:pr`), `list_pipelines` (enumerates `orgs/{org}/repos` then `repos/{repo}/actions/runs` per repo), and `fetch_members` (via `/orgs/{org}/members`). `list_runners`, `list_releases`, `list_milestones`, `list_branches`, `list_environments`, and `list_deployments` still return `Err("Org-level … not supported on GitHub")`; `list_labels` returns an empty result. Surfacing GitHub orgs in the Switch overlay (`recent_groups.json` + cached-repo remote probe) therefore exposes this partial coverage — selecting an org is safe on Issues/MRs/Pipelines/Members tabs and produces error toasts elsewhere.

**Rule:** Never use `glab api` or `gh api` when a native subcommand exists. Prefer native subcommands — they use built-in pagination, auth, and output formatting. Only fall back to raw API calls for endpoints with no native CLI equivalent.

## 2. Directory Structure

* [src/lib.rs](src/lib.rs): Library crate root (`glab_tui_crate`). Declares every module and the crate-root re-exports (`AppTerminal`, `keybinding_matches`, `spawn_refresh_active_tab`, the `git_helpers`/`templates`/`editor`/`entity_editor` globs). The binary and the fuzz targets both link it, so anything `main.rs` calls must be `pub`. Module unit tests run with `cargo test --lib`.
* [src/main.rs](src/main.rs): Binary entry point (`use glab_tui_crate::*`). Sets up the terminal and the `App`, then runs the event loop: draw, read one event, hand it to `update::update`, and execute the `Effect`s it returns (`run_effects`: `tokio::spawn` the tasks, start the threads, hand the terminal to foreground jobs and feed their outcome back through `update`, quit). Nothing else in the loop body spawns or awaits.
* [src/update/](src/update/): `update(app, event) -> Vec<Effect>`, the one place events change `App`. It never awaits or spawns: every task, thread and terminal handoff it starts is in the returned list. `keys.rs` routes a resolved keypress (Ctrl+C / quit, the overlays in a fixed order, the global keys, then `handle_active_tab_key`), `events.rs` applies background results and mouse events, and `tick.rs` runs what waits for time (key-sequence timeouts, debounced preview fetches, the followed job log, the periodic list refresh). After every event except the passive ones (`Tick`, `Resize`, log and notice events, see `may_move_highlight`), `fetch::prefetch_highlighted` fetches what the highlighted row's preview needs and is not cached.
* [src/effect.rs](src/effect.rs): `Effect` (`Spawn(Task)`, `SpawnThread`, `Suspend(ForegroundJob)`, `Quit`) and `Effects`, the list handlers push onto (`fx.spawn(..)`, `fx.spawn_cancellable(..)` which returns the `CancelHandle` that drops the task with it, `fx.spawn_thread(..)`, `fx.suspend(..)`, `fx.quit()`). `ForegroundJob::run` is what the executor does with the terminal: view the open job log or a deployment log, edit a text for an `EditPurpose`, or run custom commands in the foreground.
* [src/app.rs](src/app.rs): Contains the global `App` state, data models for UI components (`EditMenu`, `SubmitDialog`, `Selector`, `DiffView`, `DatePicker`), and fuzzy-filtering logic.
* [src/config.rs](src/config.rs): Config, theme, and icons system. Defines `Config`, `Theme`, `ThemeOverrides`, `Icons`. `Config::keybindings` is a `keymap::Keymap`.
* [src/keymap.rs](src/keymap.rs): The action registry (`Action`, `ActionSpec`, `ACTIONS`, `KeyContext`, `Support`) and `Keymap`, the per-action keys read from `[keybindings.<table>]`. See Keybinding System below.
* [src/event.rs](src/event.rs): Defines the `Event` enum and the async `EventHandler` using `tokio::sync::mpsc`.
* [src/backend/](src/backend/): CLI backend layer.
    * [bounded_output.rs](src/backend/bounded_output.rs): `output_bounded`, the subprocess reader behind the command runners. Keeps at most a given number of stdout bytes and kills a child that writes more.
    * [rate_limit.rs](src/backend/rate_limit.rs): `ApiRateLimiter` — automatic 429/graphql rate-limit detection and retry with exponential backoff plus bulk-operation pacing (`pace_bulk_operation`).
    * [subprocess.rs](src/backend/subprocess.rs): `subprocess::output(&mut Command, input)` — the one way to run a `gh`/`glab` call: pipes stdout/stderr, writes `input` to stdin, and kills the child once it outlives `command_timeout_seconds` (`config::command_timeout()`), returning an error that names the command. `output_capped` does the same keeping at most a given number of bytes of each stream and draining the rest, so the child still runs to completion.
    * [logged_command.rs](src/backend/logged_command.rs): `LoggedCommand`, how every runner reports a finished `glab`/`gh`/`git` call to the Terminal tab: `start` before spawning, `finish(tx, status, ChildOutput)` sends `Event::TerminalCommandLogged` with the entry's `Execution` (start time, duration, exit code, stdout/stderr cut to `MAX_CAPTURED_OUTPUT_BYTES`, and the `Invocation`). `failure_reason(&ChildOutput)` is the reason every runner and `rerun` put after `Failed: ` (trimmed stderr, else the command and how it ended, plus GitHub's error details from the body of a `gh api` call). `rerun(invocation)` runs a recorded call again through `subprocess::output_capped` (one byte past `MAX_CAPTURED_OUTPUT_BYTES` per stream) under one `RATE_LIMITER` slot. New runners must log through it so their entries can be inspected and re-run.
    * [mod.rs](src/backend/mod.rs): `Backend` trait with ~40 methods covering all API interactions plus `IssueUpdate`/`MrUpdate` field structs for batched entity edits and `NewIssue`/`NewMr`/`MergeOptions` for creation and merge calls.
    * [glab.rs](src/backend/glab.rs): `GlabBackend` — shells out to `glab` CLI.
    * [gh.rs](src/backend/gh.rs): `GhBackend` — shells out to `gh` CLI.
* [src/domain/](src/domain/): Domain models and top-level API functions.
    * [client.rs](src/domain/client.rs): `GitlabClient` wrapper holding the backend, page_size, api_per_page, and event tx.
    * [issues.rs](src/domain/issues.rs): Issue structures and `list_issues`/`get_issue`.
    * [job_trace.rs](src/domain/job_trace.rs): `JobTrace` / `TraceCursor` / `TraceUpdate` and `JOB_TRACE_MAX_BYTES`: a job log read in bounded pieces, appended to by follow mode. `JobTrace::next_failure_line` finds the next line reporting a failure (`FAILURE_WORDS` in the line's `trace_line_content`, whole words that keep `-`, `.` and `/`, not next to a zero count) for the Jobs tab's `jump_to_failure` key.
    * [labels.rs](src/domain/labels.rs): `Label` structure carrying the API-provided color used for the Labels column.
    * [mr.rs](src/domain/mr.rs): MergeRequest, DiscussionNote, NotePosition structures.
    * [mr_state.rs](src/domain/mr_state.rs): MR review-state helpers — `ApprovalState`, `MergeabilityState`, `WorkflowStatus`, `derive_awaiting_you`, `rebase_gate`, and the cell/sort/filter display helpers for the Approval/Mergeable/Workflow columns.
    * [review_threads.rs](src/domain/review_threads.rs): `ReviewThread` / `ThreadAnchor` and `group_threads()` — groups MR/PR notes into discussion threads and classifies each as general, in-diff, or outdated.
    * [pipelines.rs](src/domain/pipelines.rs): Pipeline, Job and `CommitSummary` structures, job deduplication logic, and `triggering_commit()` (GitHub lists a run's commit with the run, GitLab only with each job, so the inspector reads it from the pipeline's jobs on GitLab).
    * [runners.rs](src/domain/runners.rs): Runner structures.
    * [releases.rs](src/domain/releases.rs): Release structures.
    * [notifications.rs](src/domain/notifications.rs): Notification structures (GitLab todos + GitHub notifications).
    * [milestones.rs](src/domain/milestones.rs): Milestone structures.
    * [branches.rs](src/domain/branches.rs): Branch structures.
    * [deployments.rs](src/domain/deployments.rs): Environment and Deployment structures.
    * [workflow_inputs.rs](src/domain/workflow_inputs.rs): `WorkflowInput` / `WorkflowInputType` for `workflow_dispatch` prompt fields.
* [src/fetch.rs](src/fetch.rs): Per-tab data fetches, routed through `&Scope`. `spawn_refresh_active_tab()` queues one onto `Effects`, and `refresh_tab()` is the same fetch as a future, for code already running inside a task. `spawn_refresh_all_tabs()` is the background tab prefetcher used when `config.prefetch_tabs` is enabled. `prefetch_highlighted()` fetches the highlighted pipeline's jobs, MR head pipeline's jobs or milestone's issues on a cache miss. `derive_workflow()` recomputes the derived MR `workflow` column after live fetches and cache loads.
* [src/git_helpers.rs](src/git_helpers.rs): Git helpers — `detect_backend` (remote host + CLI auth → `BackendKind`), `parse_project_path` (remote-URL → `namespace/project`), `parse_project_path_from_web_url`, `parse_group`, `parse_remote_host`, `get_current_branch`, `repo_root`, `slugify`, `get_workflow_files`.
* [src/custom_commands.rs](src/custom_commands.rs): User-defined `[[custom_keybindings.<pane>]]` commands — `CustomCommands::load` (validation, built-in shadow detection, `ConfigProblem` reports), `CommandPane` (universal / issues / mrs / jobs / branches / diff and their template arguments), gh-dash style `{{.Name}}` templating (`render`, `TemplateValues`, `GLAB_TUI_*` environment) and `shell_process` (`$SHELL -c`).
* [src/command_log.rs](src/command_log.rs): `CommandLog`, the Terminal tab's history behind `App::terminal_commands`. It keeps the newest `MAX_LOG_ENTRIES` (1,000) `TerminalCommand`s and hands out `LogRow` handles that stay valid while older entries are dropped or the log is cleared. Update entries through `find_latest` / `set_status` / `settle` / `App::settle_command`, never by position, since positions shift on every eviction. Each entry carries an `Execution` (`started_at`, `duration`, `exit_code`, captured `stdout`/`stderr`, and the `Invocation` that makes it re-runnable; entries that only describe an action have no invocation). The Terminal tab filters it with the global search bar and `StatusFilter` (`App::filtered_terminal_commands`, `cycle_status_filter` key), acts on the bottom row of the view (`App::terminal_cursor` / `selected_terminal_row`), or on the inspected entry while the inspector is open: copy command (`copy_command`), copy output (`copy_output`), re-run (`rerun_command`), and clears it (`clear_log`).
* [src/form.rs](src/form.rs): `Form`, the shared dialog model: `Group`s of a `GroupKind` (`Radio` (plain text and no focus stop with one choice), `Toggles`, `LineInput` (character counter past `soft_char_limit`, `e`/`Ctrl+E` hand it and the `Preview` right after it to `$EDITOR` as one text through `FormAction::OpenEditor`), `Preview`, `Collapsible` (opened by its `key`, which folds it only from inside), `ItemList` (bulk `Progress` per entry) and `Note` (`Info` / `Warning` / `Error`)), `Button`s with a `primary` and a `cancel` index, and `FormTone::Danger` (red border, focus and primary moved to Cancel). `handle_key` / `click_at` own the focus model and return a `FormAction` (`Activate(button)`, `Cancel`, `OpenEditor`) for the owner to carry out. `Group::loading()` plus `Form::apply_loaded(id, ..)` fill late values only into groups the user has not touched, and into the toggles of a group the user has not flipped. Groups are read back by `GroupId`, never by label or position. `key_hints()` feeds the footer.
* [src/notice.rs](src/notice.rs): `Notice` / `NoticeLevel` / `NoticeQueue` / `RequestTag`, the queue behind every toast, header notice and in-modal notice (see Unified Error Handling below).
* [src/review_submit.rs](src/review_submit.rs): `ReviewSubmit`, the submit-review overlay's state behind `App::review_submit`: `ReviewVerdict` (Comment / Approve / Request changes / Keep as draft, mapped to `ReviewEvent` by `event()`), the summary `TextBuffer`, `ReviewSubmitFocus`, `SubmissionState` (`Editing` / `Submitting { log_row, drafts }` (the drafts it sent) / `Refused(reason)` when nothing was sent / `Failed(reason)` when the server rejected it) and the last frame's `ReviewSubmitLayout` for clicks. `event_to_post` refuses an empty review with `ReviewEvent::is_empty_review`, the rule `glab-tui review submit` uses too. `clear_outcome` drops a refusal or failure once the verdict or the summary text changes.
* [src/scope.rs](src/scope.rs): `Scope` enum (`Repository` / `Group`) — `as_str()`, `is_group()`/`is_repository()`, `cli_repo_arg()`/`cli_group_arg()` (glab/gh flag injection), `api_path_prefix()` (with `%2F` URL encoding), and `Display`.
* [src/word_diff.rs](src/word_diff.rs): `changed_ranges(old, new)`, the word diff of a removed line against its replacement: both are split at UAX #29 word boundaries (`split_word_bound_indices`) and diffed with `similar::algorithms::myers` directly, since `TextDiff` compiles in every algorithm it can dispatch to (about 300 KiB of code). Returns `ChangedRanges { old, new }`, byte ranges joined across whitespace, or `None` when under half the words are unchanged (`MIN_UNCHANGED_RATIO`, a rewrite rather than an edit) or a line exceeds `MAX_LINE_BYTES`. The ratio counts only segments with a letter or digit (`unchanged_word_ratio`), since spaces and punctuation are shared by most code lines.
* [src/handlers/](src/handlers/): Keypress handlers split by concern, called from `update`. Each takes `tx: &UnboundedSender<Event>` (where its tasks report) and `fx: &mut Effects` (where it queues them): handlers never call `tokio::spawn`, `std::thread::spawn` or `.await`.
    * [mod.rs](src/handlers/mod.rs): Module declarations.
    * [tabs.rs](src/handlers/tabs.rs): Per-tab keybindings (create/edit/delete/approve/merge/view-diff etc.).
    * [overlays/](src/handlers/overlays/): One module per overlay: `submit_dialog`, `help`, `switch_repo`, `date_picker`, `review_threads`, `text_input`, `selector`, `edit_menu` and `configure` (the Configure View).
    * [diff_view.rs](src/handlers/diff_view.rs): Diff view keys, `spawn_mr_review_task` / `post_review_comment` and `add_diff_comment` (draft in review mode, else posted at once).
    * [editor_result.rs](src/handlers/editor_result.rs): Applies `Event::EditorClosed`, the text an editor saved for its `EditPurpose` (text input value, edit-menu description, draft body, pushed comment, new diff comment or suggestion).
    * [search.rs](src/handlers/search.rs): Keys while the search bar or the job log search is being typed in.
    * [refresh.rs](src/handlers/refresh.rs): The refresh key (`F5`, `Ctrl+r`, `global.refresh`), which also restarts `App::last_list_refresh`.
    * [scope.rs](src/handlers/scope.rs): Scope switching: `sync_after_scope_change`, `spawn_client_for_scope` and `apply_client_ready`.
    * [mouse.rs](src/handlers/mouse.rs): Mouse scroll and clicks over overlays and tables.
    * [custom_commands.rs](src/handlers/custom_commands.rs): `run_bound_command` resolves the highlighted row's template values and queues the custom command: a terminal run as `ForegroundJob::RunCommands` (`TerminalRuns`, run through `editor::suspend_while`), a background run on its own thread. `report_runs` logs the outcome.
    * [todos.rs](src/handlers/todos.rs): Todos tab actions (open target and mark read, mark done, mark all read, unsubscribe, show-read toggle, copy URL / reference). Read and done marks go through `spawn_marks` (paced batch, one `TodoChanged` for the accepted ids and one for the failed ones), the other mutations through `spawn_todo_change`. Both report `Event::TodoChanged`.
    * [terminal.rs](src/handlers/terminal.rs): Terminal tab keys (`handle_tab_key`), the command inspector's keys (`handle_inspector_key`, before the tab handler in the key router) and `rerun`, which logs a `RERUN_LOG_PREFIX` row and settles it from `Event::CommandRerun`.
    * [review_submit.rs](src/handlers/review_submit.rs): The submit-review overlay. `open` is its only constructor (the diff view's `r` and the leave-diff dialog's Submit). `handle_key` runs first in the main loop's overlay chain, takes the terminal for `Ctrl+E` (the summary in `$EDITOR`) and swallows every key, `Ctrl+E` included, while a submission runs. `Ctrl+C` is handled in `main.rs` instead: it is refused with a notice while a submission runs because only a successful `finish` clears the drafts the server may already hold. `submit` posts through `Backend::submit_review` without taking the drafts, records the ones it sent in `Submitting`, logs a `REVIEW_SUBMIT_LOG_PREFIX` row and sends `Event::ReviewSubmitted`. `finish` settles that row, then removes exactly the sent drafts with `App::drop_sent_drafts` (from both the pending and held-back lists, which a diff refetched meanwhile may have re-split, and from the cache) and closes the overlay on success, or keeps both and shows the error inline on failure.
* [src/utils/](src/utils/):
    * [cache.rs](src/utils/cache.rs): Offline caching at `~/.cache/glab-tui/<repo>.json` plus recent-groups state (`recent_groups.json`).
    * [format.rs](src/utils/format.rs): Time parsing, ANSI formatting, string truncation, `displayable` (text being edited as drawn, with tabs and carriage returns as one space so byte offsets hold), tab expansion (`expand_tabs`), text wrapping (`wrap_text`, and `wrap_ranges`, which keeps whitespace, measures display columns like `Span::width` so a CJK row fits the box it is drawn in, and returns byte ranges so an editing cursor maps to its row). `trace_line_content` is a job log line without the GitLab Runner timestamp, the GitLab section markers (`section_start:`/`section_end:`, with any CSI sequences in front of them) or the `<job>\t<step>\t` prefix of `gh run view --log` (only split off when a GitHub timestamp follows it), the same split `parse_ansi_trace` renders and `JobTrace::next_failure_line` searches.
    * [markdown.rs](src/utils/markdown.rs): CommonMark + GFM Markdown rendering via `pulldown-cmark`.
    * [ui.rs](src/utils/ui.rs): Wrappers for `ratatui` stateful lists and tables.
    * [private_fs.rs](src/utils/private_fs.rs): Owner-only `create_dir_all` (`0700`), `create_owned_dir` (`0700`, also tightening an existing directory) and `write` (`0600`, also tightening an existing file) for everything glab-tui persists; plain `std::fs` off Unix.
    * [update.rs](src/utils/update.rs): GitHub releases self-updater with multi-target Linux asset selection. Talks to GitHub through `curl` (never `gh`, so GitLab-only installs can update) and verifies the archive against the release's `<asset>.sha256` before extracting or replacing the running binary.
* [src/cli.rs](src/cli.rs): CLI subcommands (`doctor`, `clean-cache`, `cache`, `open`, `repos`, `review`), flags (`--config` sets `config::use_config_file`, which `Config::config_path()` honours before `GLAB_TUI_CONFIG`/XDG; `-r/--repo` and `-d/--dir` are global, and `--dir` is applied before any subcommand runs) and ANSI-styled diagnostic output.
    * [cli/review.rs](src/cli/review.rs): `glab-tui review threads|comment|submit|reply|resolve` — non-interactive review for scripts and agents. JSON on stdout, errors on stderr with a non-zero exit. `--input` is a JSON array of `{ file, line, end_line?, side?: "old"|"new", body }`; anchors are checked against the diff (`DiffView::new` + `DiffView::contains_anchor`, same classification as the review threads overlay) before anything is posted. `threads` prints `ReviewThread::id` as the thread id. On GitHub it also prints the PR's conversation comments and review summaries as `general` threads keyed by their node id (`IC_…` / `PRR_…`), with `"resolvable": false`. A review summary adds `review_state` (`ReviewState`, e.g. `CHANGES_REQUESTED`) and its note `id` is `null`. Plain comments, inline threads and GitLab output carry no `review_state`. `reply` and `resolve` given one of those node ids fail in `GhBackend::reply_to_thread` / `set_thread_resolved` before any call. E2E coverage in `tests/e2e/review_cli.rs`; the `gh`/`glab` mocks append `--input -` request bodies to `<TEST_LOG_PATH>.stdin` and fail any call matching `TEST_GH_FAIL_MATCH` / `TEST_GLAB_FAIL_MATCH`. The `glab` mock also takes `TEST_GLAB_FAIL_NTH` (fail only the Nth matching call, counted in `<TEST_LOG_PATH>.fail_count`, for calls with identical arguments) and `TEST_GLAB_FAIL_MATCH_2` (a second pattern failing in the same run). `TEST_GLAB_ISSUES` names the fixture `issue list` serves.
* [src/templates.rs](src/templates.rs): Default issue/MR description templates.
* [src/editor.rs](src/editor.rs): External editor integration (`$EDITOR`/`$VISUAL`) and `suspend_and_run` / `suspend_while`, the shared terminal handoff for any foreground child process (or several in one handoff).
* [src/entity_editor.rs](src/entity_editor.rs): Edit-menu field change logic and creation form helpers.
* [src/ui/](src/ui/): Ratatui render functions.
    * [mod.rs](src/ui/mod.rs): Re-exports and shared render helpers.
    * [compaction.rs](src/ui/compaction.rs): `compact`, the ordered compaction pipeline new size-dependent layouts go through, with the workspace's preview placement (`place_preview`) and the diff view's split/unified choice (`fits_side_by_side_diff`) as its rule lists.

## 3. Core Architectural Patterns

### State Management (`App`)
* **Single Source of Truth:** All application state lives in the `App` struct inside [src/app.rs](src/app.rs).
* **No Blocking in UI:** `ui::render` ([src/ui/mod.rs](src/ui/mod.rs)) is called on every tick. Never perform I/O, API calls, or heavy computation anywhere under [src/ui/](src/ui/).

### Event Loop & Async Operations
* User input (`crossterm` events) and background task results communicate with the main loop via the `Event` enum over a `tokio::sync::mpsc::UnboundedSender`. `App::tx` holds that sender. `App::default()` holds one whose receiver is already gone.
* **`update` decides, the loop executes.** `update::update(app, event)` is synchronous and returns `Vec<Effect>`. A handler that needs background work pushes it onto `fx` (`fx.spawn(async move { .. })`), one that needs the terminal pushes a `ForegroundJob` (`fx.suspend(..)`), and the quit keys push `Effect::Quit`. Only `run_effects` in [src/main.rs](src/main.rs) spawns, and only inside a task may code call `tokio::spawn` or `.await` (e.g. `fetch::refresh_tab(..).await` after a mutation).
* **Adding an API Call:** When adding a new API call:
    1. In the handler (reached from `update`), queue a task with `fx.spawn(async move { .. })`.
    2. Make the API call using `app.gitlab_client`.
    3. Send an `Event` back to the main thread (e.g., `tx.send(Event::MyDataFetched(data))`). Fetches whose result belongs to the current repo/group send through `app.scoped_sender(tx.clone())` (an `event::ScopedSender`): it tags the event with `app.scope_generation`, which `reset_on_scope_change` bumps, and the event loop drops results from an older generation before any handler runs, so a fetch that outlives a scope switch never writes into the new scope's tabs or cache.
    4. Handle the event in `events::apply` ([src/update/events.rs](src/update/events.rs)) to update `app` state.
* **`CommandCompleted` carries a typed outcome.** `Event::CommandCompleted(tab, Ok(CommandOutcome::Mutated))` refetches `tab` and the open diff. `Ok(CommandOutcome::ReadOnly)` (opening a page in the browser, downloading an artifact) only marks the Terminal-tab entry a success. Pick `ReadOnly` for any success that changes nothing glab-tui lists. Turn a call's `anyhow::Result<()>` into that result with `CommandOutcome::mutation(result)` / `CommandOutcome::read_only(result)`.
* **Never await a remote CLI call inside a key handler.** Handlers are synchronous and run on the main loop, so a remote `glab`/`gh` call is queued as a task and its result applied from an `Event` (e.g. `spawn_open_pipeline` → `Event::PipelineOpened` → `apply_opened_pipeline`, which drops replies for a pipeline no longer listed). Local-only `git` reads that [src/git_helpers.rs](src/git_helpers.rs) documents as safe on the UI thread (`get_current_branch`, `get_default_branch`, `repo_root`) are synchronous and may run inline. Inside a task they go through `tokio::task::spawn_blocking`. A `git` call that can reach the network, such as `git fetch`, is spawned like a remote call.
* **Input runs on a dedicated OS thread** (`EventHandler::new` in [src/event.rs](src/event.rs)): crossterm's `poll`/`read` block and must never occupy a tokio worker.
* **Scope switches build the client off the loop.** `spawn_client_for_scope` clears `app.gitlab_client` and runs `GitlabClient::new` (`git remote` + `gh`/`glab auth status`) in a task. Its `Event::ClientReady { scope, result }` goes through `app.scoped_sender`, so a build that a later switch superseded is dropped by generation, even one for the same scope. `apply_client_ready` installs the client that survives and starts the refresh.
* **Preview prefetch follows state transitions.** `fetch::prefetch_highlighted` runs after every event that can move the highlight or change the cache (keys, mouse, fetched lists, `PipelineJobs`, `ClientReady`, ...) and once at startup, never on a bare `Tick`. A new `Event` variant that only logs or notifies belongs in `update::may_move_highlight`'s passive list.

### External Editor Integration
* The application pauses the UI to open an external `$EDITOR` (or `$VISUAL`, defaulting to `helix`).
* Handlers ask for it with `fx.suspend(ForegroundJob::..)`. The loop runs the job with the terminal and feeds its outcome back through `update`: `Event::EditorClosed { purpose, text }` for an edit (applied by [src/handlers/editor_result.rs](src/handlers/editor_result.rs)), `Event::ViewerFailed` for a read-only view that could not open, `Event::CustomCommandFinished` for custom commands. A new edit target is a new `EditPurpose` variant, never a closure.
* This is done using `crossterm::terminal::LeaveAlternateScreen` inside `editor::suspend_and_run` ([src/editor.rs](src/editor.rs)), which `edit_in_editor`, `view_in_editor` (read-only display, e.g. the Jobs tab's job trace) and custom commands (via `suspend_while`) share. It also holds off SIGINT/SIGQUIT in glab-tui while the child owns the terminal, so Ctrl+C stops the child only. Any other foreground child process must go through it too. Do not reinvent this wheel.
* Always build the editor process with `editor::editor_command`, which runs `$EDITOR` through the shell so values with arguments (`code --wait`) work. The job-trace editor key fetches the trace first when it is not loaded (`App::pending_job_trace_editor`, consumed on `JobTraceFetched`).

### Syntax Highlighting (`syntect`)
* All syntect use lives in [src/syntax.rs](src/syntax.rs). `SYNTAX_SET` is a `LazyLock` over `two_face::syntax::extra_newlines()` (bat's grammars: syntect's defaults plus TypeScript/TSX, TOML, Dockerfile, Kotlin, Swift, Nix, Zig, Terraform, Svelte, Vue, …), so `LineHighlighter::highlight` feeds every line with its `\n` restored. syntect's own `default-syntaxes` feature is off: the two sets would both be linked in. There is no syntect theme: colors come only from the app's `Theme`.
* **Stateful:** `LineHighlighter` carries the parse state from line to line. Markdown fences (`highlight_code`) and code suggestions highlight a block as one text. `DiffView::new` drives a `DiffHighlighter`, which keeps one state per side of the current file (context rows feed both, removals the old side, additions the new side) and restarts both at every hunk header.
* **Grammar detection:** `syntax_for_path` matches the whole file name first (`Makefile`, `Dockerfile`), then the extension. A file it cannot name is decided by `syntax_for_first_line` (shebang, mode line) only when its first diff row is line 1. Fences go through `syntax_for_token` (extension, then grammar name, case-insensitive). An extension bat's set gives to two grammars resolves through `EXTENSION_GRAMMARS` in [src/syntax.rs](src/syntax.rs) first, for paths and fences alike (`fs` is F#, though GLSL claims it too): add such an extension there, never as a fence alias. `resolve_syntax_lang` in [src/utils/markdown.rs](src/utils/markdown.rs) only maps the fence tokens that name no grammar by themselves (`python3`, `shell`, `csharp`, `fsharp`) to a grammar name.
* **Theme-safe:** `DiffLine::syntax_highlighted` stores `SyntaxToken { kind: TokenKind, range }` runs over `DiffLine::code()` (the line without its diff marker), never resolved colors. Renderers call `DiffLine::syntax_spans(&theme)` / `styled_tokens`, which map each `TokenKind` to a theme token via `TokenKind::style`, so a theme reload recolors an open diff. Scope names are classified once per interned `Scope` by `ScopeKinds`. A token takes the kind of its innermost non-`meta.*` scope: region scopes such as `meta.method.body.java` stay open across lines and would otherwise color every identifier inside them.
* `DiffView::without_highlighting` parses the same structure with no highlighting and no word marks. The headless `glab-tui review` subcommand uses it, since it only checks anchors.

### Entity Inspector & Form Architecture (`src/ui/inspector.rs`)
* **Unified Render Pipeline:** Read-only details preview and interactive edit/create modes share a single rendering path driven by `render_entity_inspector(f, ctx, &doc, area, mode, &label_colors)`. `InspectorMode` (`ReadOnly` vs `Interactive`) is the only structural switch, and `EntityDocument` is the single source of truth for both modes.
* **Single-Column Layout:** The markdown description spans full-width at the top, and the metadata fields list is cleanly stacked beneath it with aligned `│` separators.
* **Navigation & Inline Editing:** In interactive mode, `j`/`k`/arrows navigate across all editable rows including Description/Release Notes. `Enter` toggles inline editing (or opens external `$EDITOR` / `Ctrl+E`). `ReadOnly` and `Section` spacer fields are skipped during interactive navigation and render with a muted shield icon (`readonly` nerd font icon).
* **Mode Indicators:** The top banner right-aligns a vim/helix-style mode badge (`[NORMAL]`, `[PREVIEW]`, `[EDIT]`, `[CREATE]`) mapped to semantic badge theme colors. Pressing `Esc` in edit forms pops back to the previous zoom state predictably.
* **In-Menu Creation Forms:** Issue and MR/PR creation forms embed "Create from Issue" (fuzzy-searches existing issues, populates fields, links via `--related-issue` on GitLab or `Closes #N` on GitHub) and "Description Template" rows directly in the menu.
* **Bulk Edit Selection:** Bulk edit menus carry `InspectorContent::Custom` displaying the full list of selected `#iid` / titles in the descriptor pane so users can verify affected entities before submission.

### Visual Select Mode (Yazi-Style)
* `v` (`selection_toggle` keybinding) toggles select mode on the Issues, MRs, and Branches tabs. Navigating (`j`/`k`/arrows) paints row selection dynamically.
* Selected rows display a 1-wide leftmost colored bar (`checked_bg`) and the top-right header shows a `[SELECT]` mode badge.
* `Space` (`select_issue` / `select_mr` / `select_branch`) continues to toggle individual item selection.

### Unified Error Handling (`App::show_error`) & Notice Queue
* All user feedback lives in one queue, `App::notices` (`NoticeQueue` in [src/notice.rs](src/notice.rs)). A `Notice` has a `NoticeLevel` (`Info` / `Error`), its text, an optional `detail` line and an optional `origin: RequestTag`. A newer notice replaces only an older one of the same level and origin, which no surface could draw any more, so a burst of info notices never evicts a live error: each surface draws the newest notice meant for it, and `App::tick` (the `Event::Tick` update step) drops notices older than `NOTICE_LIFETIME` (5 seconds), except those routed to the open modal, which stay until it closes. Render code only reads the queue (`App::toast_notice`, `App::header_notice`, `App::modal_notice`) and never expires or clears anything. The toast and header lookups (`NoticeQueue::latest_outside`) still skip a notice past its lifetime, so a modal's notice kept past it does not come back as a toast in the frame drawn as the modal closes, before the next tick drops it.
* All API errors, network failures, and guard violations route through `App::show_error(msg)`, or `App::show_cli_error(msg)` when the failed glab/gh call's stderr is in the Terminal tab (the toast then adds `CLI_LOG_HINT` as its detail line). `App::raise_error_toast` raises an error without marking a terminal entry, for failures already recorded with `record_command_outcome`.
* Errors display as a 3-row floating rounded toast box with `status_failed` icon (4 rows with a detail line).
* `show_error` automatically stamps the most recent running command in the terminal commands bar as failed, keeping both UI surfaces synchronized.
* **Modal routing:** a modal that starts a request takes a tag from `App::next_request_tag()`, stores it, and the request's reply event carries it back. Notices built with `Notice::from_request(tag)` are drawn inside that modal (`MODAL_NOTICE_ROWS` row at its bottom) while `App::open_modal_request()` returns the same tag, and fall back to the toast or header bar once the modal closed. Today the field-value `Selector` (`Selector::request`, `Event::SelectorItemsFetched { request, items }`) is the modal wired this way: `App::apply_selector_items` shows its fetch failure and offline-cache fallback inside the selector, and drops a reply whose tag the open selector no longer holds (it compares against the selector's own tag, not `open_modal_request`, so another modal on top cannot drop it). Add a new modal's tag to `open_modal_request`, and match its replies against that modal's own tag. Its mouse handler must also leave the notice row out of the clickable list while `App::modal_notice()` returns a notice, as the `Selector` arm of the mouse handler does by adding `MODAL_NOTICE_ROWS` to the `footer_rows` it passes to `handle_selector_mouse`. The row sits below the list, so item clicks do not shift without it, but a click on the notice row would resolve to the item just past the visible list.
* Non-error feedback goes through `App::show_notice(text)`, rendered muted in the header bar. `App::clear_info_notices()` takes down header notices once what they announced has landed (errors stay until they expire). Stale data is tracked per tab in `App::stale_tabs` (`Tab → StaleData`) and drawn as a red badge next to the notice only while that tab is active: `App::mark_cached_tabs_stale` flags every tab filled from the offline cache, a `FetchFailed` over cached rows flags its tab `RefreshFailed` instead of toasting, and only that tab's own `*Fetched` arm clears it. Because of that, only list refreshes send `FetchFailed`: other background failures send `CommandCompleted(Err)`, and background successes send `Event::Notice`.
* Background mutations never discard their `Result`. Optimistic pipeline/job status flips go through `run_optimistic_mutation` ([src/handlers/tabs.rs](src/handlers/tabs.rs)): failed rows are restored via `PipelineStatusRevert`/`JobStatusRevert`, and all failures surface as one `CommandCompleted(Err)` toast. A failed fetch sends exactly one error event.

### Jobs Tab (current branch)
* `fetch::fetch_current_branch_jobs` reads the branch with `git_helpers::get_current_branch`, then asks `Backend::find_branch_pipeline_id` for the newest pipeline of that branch (on GitLab also its open MR's `refs/merge-requests/<iid>/head` pipeline). Never list every MR or pipeline to find it.
* Starting a manual job is GitLab only. On GitHub the `start_job` key is omitted from the help overlay and does nothing when pressed (it is still consumed, so the custom-command shadow report stays accurate).
* The preview goes through `render_entity_inspector` with `entity_editor::build_job_document`: the highlighted job's metadata above the pipeline's stage summary, or, while a trace is open or loading, as a fields-only header above the separate `Trace` pane (`render_job_trace`). The header is sized from its wrapped field rows (`inspector::read_only_fields_height`, since a `List` drops an item that does not fit whole) and capped at half the pane, so the log keeps most rows.
* Scrolling the log to a line goes through `App::scroll_job_trace_to_line` (it also clears `detail_scroll_to_bottom`, which would override the jump), resolved by `render_job_trace` with `JobTraceView::jump_to_line`, because only the draw knows the wrapped width. `jump_to_failure` (`E`) searches from `JobTraceView::failure_search_start()`, so a failure on the last page, which the scroll clamp keeps from reaching the top of the pane, is passed on the next press; without a trace it fetches one and sets `App::pending_job_trace_failure`, consumed on `JobTraceFetched` like `pending_job_trace_editor`.
* `copy_url` (`y`) copies `Job::web_url` (GitLab `web_url`, GitHub `url` from `gh run view --json jobs`) and `copy_id` (`Y`) the job id. `copy_sha` defaults to `Alt+y` on this tab. `open_in_browser` (`o`) opens `Job::web_url` through `GitlabClient::open_job_url`.

### Environments Tab (deployments, rollback, stop)
* `view_deployments` (`Enter`) fetches the highlighted environment's deployments, and `Event::DeploymentsFetched` goes through `App::show_deployments`, which ignores an environment no longer highlighted and keeps the focus and the selected deployment (by id) when the shown environment is refetched. `App::discard_stale_deployments` drops them once another environment is highlighted.
* `EnvironmentDeployments::is_focused` decides where navigation goes: `handlers::tabs::handle_focused_deployments_key` takes `j`/`k`/arrows/`Home`/`End` and `Esc`/`Backspace` (unfocus) before the environment list sees them. Focus only counts while the detail pane is on screen (`detail_visible` and a `detail_rect` from the last frame), so hiding it with `q` or a terminal too short to stack it below the list hands the keys back to the environment list. `focus_deployments` defaults to `Tab`, which is also `global.configure`, so the event loop skips the configure check while `App::is_deployments_focus_key` holds (deployments listed on the Environments tab). `,` still opens the Configure View there.
* The detail pane shows the deployments table over `build_deployment_document` for the selected one. Without listed deployments it shows `build_environment_document`, whose content lists the configured action keys.
* `rollback_deployment` (`R`) and `stop_environment` (`d`) open `ConfirmAction::RollbackDeployment` / `StopEnvironment` (both default to Cancel). GitLab rolls back by re-running the deployment's job (`Deployment::job_id`), so a deployment without one is refused before the dialog opens. GitHub rolls back by creating a deployment of the commit, which deploys nothing by itself: it only takes effect once a workflow running `on: deployment` picks it up, and the dialog says so. A successful rollback refetches the environment list and its deployments.
* `view_deployment_log` (`e`) fetches the deployment job's trace and opens it in the editor from `Event::DeploymentLogFetched`. Like `pending_job_trace_editor` on the Jobs tab, `App::pending_deployment_log` records the request: a second `e` while it is in flight starts no second fetch, and `App::take_pending_deployment_log` opens the log only while that deployment is still selected on the Environments tab. GitHub deployments carry no job, so like `start_job` the key is left out of the help overlay and of `build_environment_document`'s action list there, and pressing it is still consumed and raises an error.

### Pipelines Tab
* `Enter` descends into a pipeline, so the inspector is opened with `toggle_preview` (`i`). `build_pipeline_document` ([src/entity_editor.rs](src/entity_editor.rs)) shows the triggering commit, a red `Failed Jobs` count, and `InspectorContent::PipelineStages` lists each failed job with `Job::failure_reason` above the stage list. GitLab fills `failure_reason` from the jobs API (`script_failure` → `script failure`), GitHub from the job's timeout or its first failed step (`github_job_failure_reason`).
* The inspector's failed jobs and the `Stages` dots come from `app.pipeline_jobs`, which the highlight prefetch fills only for pipelines it does not hold. `PipelinesFetched` calls `App::drop_jobs_of_changed_pipelines` (compared against the root level, also inside a descent) to forget the jobs of every pipeline whose status changed, `ChildLevelFetched` does the same for the children on screen through `App::drop_jobs_of_changed_children`, `App::descend_into` forgets the jobs of every child it enters, and `spawn_pipeline_retry` forgets the retried ones, so none shows the previous outcome.
* `r` and `R` share `spawn_pipeline_retry` (`PipelineRetry::Pipeline` / `FailedJobs`) in [src/handlers/tabs.rs](src/handlers/tabs.rs). `Backend::retry_failed_jobs` is `gh run rerun --failed` on GitHub. On GitLab it lists the pipeline's failed jobs and retries each one, because the pipeline retry endpoint also reruns canceled jobs.
* `s` steps the Pipelines `Status` column filter through `PIPELINE_STATUS_FILTER_CYCLE` with `App::cycle_pipeline_status_filter`; it reuses `column_filters`, so the Configure View picker shows and clears the same filter.

### Rate Limiting (`src/backend/rate_limit.rs`)
* `ApiRateLimiter` is a global (`RATE_LIMITER`) that shields every `glab`/`gh` CLI call from HTTP 429 and GitLab GraphQL rate-limit errors.
* Backend command execution delegates to `rate_limit::execute_with_retry` (used by both `GlabBackend` and `GhBackend`), which:
  - acquires a concurrency slot via `RATE_LIMITER.pace_request()` (bounds concurrent subprocesses to `MAX_CONCURRENT_REQUESTS` and enforces a minimum inter-request burst delay) for the duration of one attempt only; the slot is released before any backoff sleep,
  - retries failures that `is_rate_limit_error()` recognizes (`429` as an HTTP status such as `HTTP 429` or `GET <url>: 429`, never bare digits like `#429`; `rate_limit`, abuse-detection, `retry-after`) with exponential backoff plus per-thread jitter up to `MAX_RATE_LIMIT_RETRIES`,
  - bubbles up immediately on non-rate-limit errors so the UI shows the real failure.
* Every `gh`/`glab` API call (the four backend runners, the diff view's comment edit/delete and release creation) runs through `subprocess::output`, so a hung CLI (e.g. a credential helper waiting on a prompt) is killed after `command_timeout_seconds` (config, default 120, reloaded with `config::reload_command_timeout()` on repo switch) instead of holding its slot forever. New API calls must use it too, never `.output()` on a `gh`/`glab` `Command`. Not covered: the self-updater (`perform_self_update`: its `gh release view` calls and the large `gh release download`), the `auth status` probes in `git_helpers` (blocking `std::process` in `spawn_blocking`) and `web--browse`.
* Bulk operations (merging, editing many MRs/issues, etc.) call `pace_bulk_operation()` before each item to avoid tripping secondary rate limits during batch loops.

### Bounded CLI Output, Job Logs & Follow Mode
* The command runners (`run_glab_command`, `run_gh`, `run_git_command`) read output through `bounded_output::output_bounded` ([src/backend/bounded_output.rs](src/backend/bounded_output.rs)). With `Some(limit)` it keeps the first `limit` bytes of stdout and kills the child once it writes more (`CapturedStdout::is_truncated`). Stderr is capped at 64 KiB and drained past that. Plain `run_glab_command` / `run_gh` pass `None` (read everything). Output whose size a third party controls (job logs, diffs) goes through `run_glab_capped` / `run_gh_bounded` with a limit. Only capped reads are killed when their future is dropped: an uncapped run (every mutation, e.g. merge) finishes even if glab-tui quits first.
* Job logs are read up to `JOB_TRACE_MAX_BYTES` (16 MiB) into a `JobTrace` ([src/domain/job_trace.rs](src/domain/job_trace.rs)). It tracks the bytes read (`TraceCursor`), holds a UTF-8 character split across reads until it completes, and records truncation. A truncated log shows `[TRUNCATED: first 16 MiB]` in the Jobs pane title, and follow mode stops polling it.
* Follow mode (`f`) is GitLab only: on GitHub the key is omitted from the help overlay and does nothing when pressed (it is still consumed, so the custom-command shadow report stays accurate). It polls `Backend::get_job_trace_since(cursor)` every 5 seconds (`Event::JobTraceFollowed`). `app.job_trace_poll_in_flight` keeps the log on screen meanwhile. A poll moves the pane to the bottom only when it brought text (`TraceUpdate::has_new_text`), so a quiet log can be read further up with follow on. Closing the log, or dropping it because the selected job or the job list behind it changed (`App::close_job_trace`), ends follow mode. GitLab reads `?byte_offset=&byte_limit=` starting 1 KiB before the end of what was read, checks that the reply starts with those bytes, and loops in chunks of at most 500 KiB (GitLab's `byte_limit` maximum). Each reply is sorted by `classify_ranged_reply` (a pure function with unit tests, so new reply cases go there). A server that ignores the parameters (it predates them) is detected from the reply, remembered per project in `PROJECTS_IGNORING_TRACE_RANGES` (process-wide, since every `GitlabClient` clone builds a fresh backend), and polled with full bounded reads. A log that no longer starts with what was read is replaced (`TraceUpdate::Restart`). GitHub returns nothing new without a CLI call: `gh run view --log` serves only completed jobs, whose logs never change.
* `app.job_trace` is a `JobTraceView` ([src/ui/job_trace.rs](src/ui/job_trace.rs)). It parses only text added since the last frame (plus the still incomplete last line), keeps the wrapped row offset of every line per width, re-parses everything only after a theme change or a restart, and gives the renderer only the visible lines. Never call `parse_ansi_trace` on the whole log from render code.
* Diffs (`get_mr_diff`, `diff_pr_in_checkout`) are read up to `MR_DIFF_MAX_BYTES` (32 MiB). A larger diff fails with an error (`ensure_complete_diff`) instead of showing a partial diff that a review could be submitted against.

### Code Review & Diff System
* **Diff view** supports inline comments, code suggestions, draft reviews, dynamic gutter sizing, and tab expansion:
  - `DiscussionNote` / `NotePosition` structs in [src/domain/mr.rs](src/domain/mr.rs).
  - `list_mr_notes()` fetches notes for an MR via the API.
  - Draft comments are the open diff's working copy in `app.draft_comments: Vec<DraftComment>` (`DraftComment` / `ReviewEvent` live in [src/domain/review.rs](src/domain/review.rs)) and are submitted atomically. Every add, edit, delete, discard and submit calls `App::persist_draft_comments(project_path, mr_iid)` with the open diff's `DiffView::project_path`, which mirrors them into `ProjectCache::draft_comments` (`project_path → mr_iid → Vec<DraftComment>`) and saves the cache, so drafts survive closing the diff and restarting. The project is part of the key because a group-scope cache is shared by every project in the group and the same iid recurs across them.
  - `DiffFetched` restores drafts through `App::restore_draft_comments`, which checks each one with `DiffView::contains_draft_anchor` (its first and, for a range, last line through `contains_anchor`). Drafts whose lines left the diff go to `app.stale_draft_comments` with a toast giving the count: they are never shown or submitted, `persist_draft_comments` writes them back with the rest, and they load again once their lines are back. `Keep drafts` and `Discard` treat them like the other drafts.
  - Every review mutation goes through `Backend::submit_review` / `reply_to_thread` / `set_thread_resolved`; the diff view and the `glab-tui review` subcommand share them. A comment posted outside review mode is a one-comment `submit_review`. Do not shell out to `gh api` / `glab api` for reviews from the event loop.
  - Current (already-pushed) comments live in `app.current_comments: Vec<DiscussionNote>`.
  - Diffs load through `fetch::fetch_diff_view`, which builds the `DiffView` on a blocking thread (parsing and highlighting a large diff takes seconds) and sends `DiffFetched { diff_view, comments }`; the "Fetching Diff" overlay stays up until it arrives. `D` is ignored while `app.diff_loading` is set, so a second press cannot start a second fetch.
  - The parser in `DiffView::new` follows each hunk's `@@` line counts: while a hunk still owes lines, every line is content, so a removed `-- comment` (`--- comment`) or added `++ x` is never read as a file header. `\ No newline at end of file` is a `Meta` row with no line numbers. Paths are read with `parse_diff_git_paths` / `parse_patch_header_path`, which keep spaces and decode git's C-style quoting.
  - Leaving the diff view with pending drafts opens the `SubmitDialog` (`ConfirmAction::SubmitReview(mr_iid)`) with `Submit`, `Keep drafts`, `Discard` and `Cancel`. `Esc`/`Cancel` only close the dialog and return to the diff with drafts and `in_review_mode` untouched. `Keep drafts` closes the diff and leaves the drafts in the cache. `Discard` deletes them (memory and cache) and closes the diff. `Submit` opens the submit-review overlay.
  - Reviews are submitted from the dedicated submit-review overlay (`App::review_submit`, `handlers::review_submit`), never a `Selector`. It stays open while the review is posted and on failure, so drafts are only cleared once `Event::ReviewSubmitted` reports success. Keep as draft closes it and leaves the drafts pending.
  - Open diff key is `D` (remappable via `keybindings.mrs.view_diff`).
  - **Layout (split / unified):** `App::diff_layout` (`DiffLayout`: `Auto`, `SideBySide`, `Unified`) is the session's choice, never saved. `render` resolves it against the diff pane's inner width each frame (`DiffLayout::is_side_by_side` → `compaction::fits_side_by_side_diff`) and applies it with `DiffView::set_side_by_side`, which keeps the cursor on the same diff line and drops a line selection. Since it runs inside `render`, `set_side_by_side` never rebuilds the rows: `update_active_lines` keeps both `lines` and `side_by_side_lines` built, and a switch only re-indexes the active layout (`index_active_rows`: cursor clamp, `hunks`, and the search when a query is set). A side-by-side row pairing a removal with an addition shows two unified lines, so going back to unified returns to the line the cursor left (`unified_cursor_before_split`) while the row under the cursor still shows it. Hunk headers and meta lines carry no line numbers, but `build_side_by_side_lines` gives each exactly one row, in order, so they map between the layouts by ordinal (`is_marker`), never by content, which repeats across hunks and files. `render` leaves the layout alone while a line selection is active, so resizing or toggling the file tree never drops it. Only the draw knows the pane width (file tree shown or not, terminal resized), like `job_trace_scroll_to_line`. `1` / `2` pin side-by-side / unified, `d` pins the other layout, `0` returns to `Auto`. All four keys go through `set_layout(app, diff_view, DiffLayout)` in [src/handlers/diff_view.rs](src/handlers/diff_view.rs), which applies a pinned layout at once. They are the registry actions `DiffLayoutSideBySide`, `DiffLayoutUnified`, `DiffLayoutAuto` and `DiffToggleSideBySide` (`[keybindings.diff]` `layout_side_by_side`, `layout_unified`, `layout_auto`, `toggle_side_by_side`).
* **GitHub diffs over 20,000 lines:** GitHub refuses to serve them (`gh pr diff` fails with HTTP 406 `PullRequest.diff too_large`). `GhBackend::get_mr_diff` then builds the diff with git in the clone `cache::find_local_checkout` finds for the PR's repository (`diff_pr_locally` / `diff_pr_in_checkout` in [src/backend/gh.rs](src/backend/gh.rs)). It only fetches (skipped when both commits are already local) and diffs — no checkout, no branch, no index or working-tree change. Without a known clone the error says a local clone is needed; every other `gh pr diff` error is returned unchanged. Review comments and review submission are unaffected: they go through the API with the same path/line anchors. E2E coverage: `tests/e2e/pr_diff_fallback.rs`.
* **Dynamic line numbers & tab expansion:** Gutter width is dynamically calculated in `DiffView::new` from the widest line number in the diff (floored at 4). Tabs are expanded to spaces at tab stops at diff parse time (`expand_tabs`) so Go/Makefiles maintain indentation without breaking syntax highlighting or search indices.
* **Word-level marks:** `DiffView::new` pairs each run of removed lines with the added lines right after it (first with first, and so on) in `mark_changed_words`. Runs of different lengths get no marks (`mark_changed_pairs`), since pairing them by position would mark a rename against the wrong line. The `\ No newline at end of file` note does not break a run, any other row does. It stores `word_diff::changed_ranges` in `DiffLine::changed_ranges` (byte ranges over `DiffLine::code()`). `render_diff_line_content` in [src/ui/mod.rs](src/ui/mod.rs) splits the already styled spans at those ranges (`emphasize_ranges`) and sets `diff_addition_emph_bg` / `diff_deletion_emph_bg` on them, so syntax colors and fuzzy matches survive. A selected or search-matched row keeps its selection background instead. A theme without the tokens derives them by mixing 30% of the row foreground into the row background (`diff_emphasis_bg` in [src/config.rs](src/config.rs)). `apply_overrides` derives them again through it when a `[theme]` override changes a row's foreground or background without setting the emphasis token too.
* **Suggestion rendering:** `format_comment_with_suggestions()` in [src/ui/helpers.rs](src/ui/helpers.rs) parses ` ```suggestion ` blocks from comment bodies and renders them as in-line diff (red for original, green for suggested).
* **Reviewed-file marks:** `m` toggles `DiffView::reviewed_files` (a `HashSet` of diff-relative file paths) for the selected file, or for every file below the selected directory; `M` toggles `DiffView::hide_reviewed`. Both are purely local — neither GitLab nor GitHub's "viewed" state is synced.
  - The tree is flattened through `DiffTreeNode::flatten_ex(depth, prefix, reviewed, hide_reviewed, out)`, which stamps `FlatDiffTreeNode::is_reviewed` (on a directory: every file below it is reviewed) and, when filtering, drops reviewed files plus directories left with no unreviewed file.
  - `DiffTreeNode::sync_expansion_to_review(before, after)` folds a directory when it becomes fully reviewed and unfolds it when it stops being fully reviewed, cascading up through parents.
  - Marks persist in `ProjectCache::reviewed_files` (`mr_iid → Vec<String>`), written via `App::store_reviewed_files_for_mr` + `save_cache` on every toggle and re-seeded by `DiffView::restore_review_state` on `DiffFetched`.
* **Review threads overview:** `T` in the diff view opens `App::review_threads` (`ReviewThreadsOverview`), a snapshot of `current_comments` grouped by `group_threads()` and classified against the diff via `DiffView::contains_anchor`. It is rebuilt on every `DiffFetched`, so resolve/reply/edit results show up after the automatic re-fetch.
  - Anchor matching for inline rendering, the `a` actions and the overview all go through `note_position_anchors()` in [src/app.rs](src/app.rs); do not re-inline the predicate.
  - `Enter` calls `DiffView::jump_to_anchor`, which falls back to the file's first row for outdated anchors. A file out of reach in the tree is revealed first (`DiffTreeNode::expand_path_to` unfolds its directories; a file hidden by the reviewed filter turns `hide_reviewed` off, and the handler syncs `app.hide_reviewed_files`). `a` reuses `Selector::comment_actions` / `Selector::comment_choice`, the same builders the line-level `a` key uses.
  - `j`/`k` wrap around like `Selector` and `StatefulList`; mouse scroll clamps, as the Selector's does.
  - E2E coverage lives in `tests/e2e/review_threads.rs`, driven by the `mr list` / `mr diff` / `mr note list` branches of `tests/mocks/glab` and the `mr_diff.txt` / `mr_notes.json` fixtures, and on GitHub by the `pr diff`, `pulls/{}/comments`, `reviewThreads` and `pr view --json comments,reviews` branches of `tests/mocks/gh` (`gh_pr_comments.json`, `gh_review_threads.json`, `gh_pr_conversation.json`).
  - GitHub's `list_mr_notes` reads three sources in one `try_join!`: review comments (`pulls/{}/comments`), their resolution (`reviewThreads`), and the conversation (`gh pr view --json comments,reviews`, `parse_pr_conversation`). Conversation comments become `NoteKind::Conversation` notes and reviews with a non-empty body `NoteKind::ReviewSummary(ReviewState)` notes (pending reviews are dropped), all with no position, so `group_threads` classifies them as `ThreadAnchor::General`. Their `discussion_id` is the GraphQL node id. A conversation comment's `id` is its REST id from the `#issuecomment-<id>` URL fragment, so Edit/Delete Comment (`issues/comments/{}`) work on it. A review summary has no REST id (`id: None`). `NoteKind::accepts_replies` is false for both, and `Selector::comment_actions` goes through it, so it offers no reply on them. It returns `None` for a note without an id (the overlay shows an error). The overlay badges a summary with its `ReviewState::label`.

### MR Review State (Approval / Mergeable / Workflow)
* The MR/PR table's `Approval`, `Mergeable`, and `Workflow` columns are derived, not fetched. `ApprovalState` / `MergeabilityState` / `WorkflowStatus` and the display/sort/filter helpers live in [src/domain/mr_state.rs](src/domain/mr_state.rs); cell text uses ALL-CAPS display strings (e.g. `CONFLICT`, `REBASE`, `CLEAN`, `APPROVED`, `AWAITING`) that the column-filter picker also shows.
* **Data sources:** GitLab fills both axes with one bulk `glab api graphql` query over `mergeRequests(iids: [...])` (batched by `api_per_page`); GitHub derives them from the review/merge fields returned by `gh pr list` (`reviewDecision`, `latestReviews`, `mergeable`, `mergeStateStatus`, `reviewRequests`) plus the current login via `gh api user --jq .login`. Either axis may be `None` (unknown) — never a guessed value.
* `MergeRequest` carries `approval` and `mergeability` as `Option<…>` and a `#[serde(skip)]` derived `workflow`. After any load (live fetch or cache read), call `derive_workflow()` in [src/fetch.rs](src/fetch.rs) to recompute `workflow` from approval state — cached rows deserialize with it unset even though the approval state it reads was persisted.
* **Rebase gating:** `rebase_gate()` in [src/domain/mr_state.rs](src/domain/mr_state.rs) decides whether `R` may rebase — `Allowed`, `ResolveLocally` (conflicts), or `NotNeeded` — surfaced as a confirm popup or a user-facing error toast. Revoking approval (`A`) is GitLab-only; `gh pr review` has no revoke path.

### Todos Tab (GitLab Todos / GitHub Notifications)
* The read filter lives on `GitlabClient::show_read_notifications` (default `false`, unread only) so every refresh path fetches with it. `App::toggle_show_read_todos` flips it and `Event::TodosFetched` carries the filter it was requested with, so a list fetched before a toggle is dropped.
* Mutations report `Event::TodoChanged(TodoChange, Result)`. `MarkedRead` / `MarkedDone` carry every id of the batch. On success `App::apply_todo_change` updates `app.todos` in place (no refetch): read and done items are restated while the tab shows them and dropped otherwise, and GitHub's done notifications always leave the list. On failure the error goes through `App::show_error`.
* Batch selection: `App::selected_todos` (notification ids) is filled by `select_todo` (Space), `selection_toggle` (visual mode through `toggle_select_mode` / `update_visual_selection`) and `select_all`. With a selection, `mark_as_read` and `mark_as_done` act on `App::todo_ids_to_act_on` (every selected todo, hidden by the search or not) and clear the selection. `mark_as_read` skips the ones already read (`App::unread_todo_ids_to_act_on`). `apply_todo_change` and `App::set_todos` drop selected ids that left the list.
* Inspector: `Enter` opens the target on this tab, so `toggle_preview` (`p`) shows the preview. `build_todo_document` renders `Notification::body` as Markdown. GitLab fills `body` from the todo list (the note text for mentions, else the target description). GitHub lists no body: `fetch::dispatch_inspected_todo_detail_fetch` (on `Event::Tick`, debounced like the PR stack fetch) reads `Notification::detail_api_path` (latest comment, else the subject) through `Backend::get_notification_detail` and sends `Event::TodoDetailFetched`, which carries the path it read: a result for a path the notification no longer has is dropped, so the next tick fetches the current one. A failure is kept in `App::failed_todo_details` and shown instead of refetching until the next list refresh, which `set_todos` treats as the retry. `set_todos` keeps a fetched body while the notification's `updated_at` is unchanged.
* `Notification::reference` (`!N` for a GitLab MR, `#N` otherwise, `None` for a target glab-tui has no view for, whose `target_iid` is not an issue number) and `type_label` (`MR` / `PR` / `Issue`) feed the ID and Type columns, the inspector, the out-of-scope error and `copy_reference`. Without a reference the ID column shows `—`, the inspector title only the type, and `copy_reference` raises an error. Search, the Type filter and group-by read `type_label` too. The raw `target_type` stays a search and filter alias, so filters saved before the label keep matching, but the picker offers only the label. The State and Type badges come from `badge_style_for`.
* GitLab todos have no read state: `mark_notification_as_read` and `mark_notification_as_done` both run `glab todo done`.
* `mark_as_read` and `Enter` share `handlers::todos::activate_todo`: a batch selection is marked read, otherwise `open_selected` jumps to the highlighted todo. The jump resolves the target in the todo's own project (`Scope::contains_project`, `App::focus_issue` / `focus_mr` with `Some(project)`) and fetches it when unlisted. A todo outside the current scope, or whose target has no view in glab-tui, raises an error instead of landing on a same-numbered item, and stays unread: `jump_to_target` returns whether it had something to open, and only then is the todo marked read.
* E2E coverage: `tests/e2e/todos.rs`, driven by `todo list` (`todos.json`) and `api todos?state=done` (`todos_done.json`) in `tests/mocks/glab`, and on GitHub by the `notifications` and `/issues/comments/` branches of `tests/mocks/gh`.

### Cache & State Persistence
* Cache directory: `~/.cache/glab-tui/` (migrated from `~/.glab-tui-cache`).
* `ProjectCache` stores `enabled_columns`, `group_by_column`, `group_ascending`, `column_filters`, `labels`, `label_colors`, `reviewed_files`, and `draft_comments` in addition to API data.
* Cache is written on every successful data fetch; read on startup.
* **Rule:** cache and config files carry private repository data and custom shell-command bindings, so every write under the cache or config directories (cache JSON, `recent_repos.json`, `recent_groups.json`, `config.toml`, themes, repo-local `.glab-tui/`) goes through `utils::private_fs`, never plain `std::fs::write` / `create_dir_all`, which would inherit the umask (`0644`/`0755` under `022`). Directories glab-tui owns outright (`~/.cache/glab-tui`, and the default `$XDG_CONFIG_HOME/glab-tui` or `~/.config/glab-tui`) go through `private_fs::create_owned_dir`, which also tightens one an older version left at `0755`: the cache path helpers (`prepare_cache_dir`) and `Config::config_path()` run on every startup, so upgraded installs are fixed on first launch. Any other directory goes through `private_fs::create_dir_all` and keeps its mode if it already exists, since the parent of a `GLAB_TUI_CONFIG` file may be user-chosen.

### Config & Theme System
* Config is loaded via `Config::load()` in [src/config.rs](src/config.rs) at startup and stored on `App` as `app.config`.
* `Config` carries an optional `backend: Option<BackendKind>` (deserialized lowercase as `"github"` / `"gitlab"`). When set it overrides automatic backend detection everywhere — startup, repo switcher, diff review submission, and `doctor` — via `git_helpers::detect_backend(remote_url, config.backend)`.
* `Config` exposes both `page_size` (total item budget per tab) and `api_per_page` (items per HTTP request, clamped to GitLab's `1–100` `per_page` range via `api_per_page_clamped()`). Thread both through the `Backend` pagination methods; `_per_request` is a no-op on GitHub, which paginates with `--limit`.
* `fetch_label_colors` (default `true`) selects between the real label colors returned by `glab label list` / `gh label list` and the theme's label palette. The API colors are stored as a `name → Color` map on `app.label_colors` (populated from the cache at startup and refreshed on `RepoAttributesFetched`); light GitHub-style label colors fall back to the theme palette because they are unreadable as foreground text on dark themes (`is_light_color()` luminance check in [src/ui/helpers.rs](src/ui/helpers.rs)).
* `Config::load()` only reads existing config files (global then repo-local) and merges overrides; it **never** writes. `config.toml` is created solely by an explicit save (`save_layout` via the Configure View submit button), targeting either global (`~/.config/glab-tui/config.toml`) or repo-local (`.glab-tui/config.toml`). If no config file exists, the app boots from in-memory defaults.
* Theme selection: `Config` holds a `theme_preset: Option<String>` and optional per-color `ThemeOverrides`. `App::apply_config()` resolves the final `Theme` from `app.config` into `App::theme` (at startup, after a repo switch reloads the config, and when the theme picker sets `theme_preset`), so a theme change never re-reads the config file. `Theme::default()` derives directly from `src/themes/default.toml` — there is no hardcoded in-code fallback, so the bundled TOML is the single source of truth. Invalid user theme overrides automatically fall back to bundled presets.
* Icons: `App::icons` (an `Arc<Icons>`) is built by `App::apply_config()` from `Config::icons` (`IconSet::Nerd` default, or `IconSet::Ascii` via `icons = "ascii"`) through `IconSet::icons()`. Code outside rendering that needs a glyph (`Tab::title`, `build_mr_document`, the `mr_state` cell helpers) takes `&Icons`; the `mr_state` sort keys and filter values read `approval_tone` / `mergeable_tone` / `workflow_cell_word`, which need none. `Icons::ascii()` keeps every glyph a single ASCII character for terminals without a Nerd Font, whose Private Use Area fallbacks render double-width and break layout. **Rule:** never write a glyph literal in render code; add a field to `Icons` and fill it in both `Icons::nerd()` and `Icons::ascii()`.
* Built-in theme presets are compiled into the binary via `include_str!` in `BUNDLED_THEMES` (38 presets including `oled`, `github-dark-hc`, and the Rosé Pine set). User themes in `~/.config/glab-tui/themes/` take precedence.
* **Semantic tokens & transparent backgrounds:** `group_by` banner styling uses the `badge_group_bg` token, and an empty color string in theme TOMLs maps to `Color::Reset`, letting the terminal's own (possibly transparent) background show through instead of painting a solid fill.
* **Form tokens:** `accent` (selected radio, input counter), `key_hint` (footer keys), `danger_border` (danger-tone frame) and `backdrop_dim` (screen behind an open form, readable but receding) are set in every bundled theme TOML (`every_bundled_theme_sets_the_form_tokens_itself` checks it) and fall back to `purple`, `yellow`, `red` and `text_muted` for user themes that omit them.
* **Rule:** Never hard-code RGB colors outside `src/themes/*.toml`. Add new semantic tokens (`diff_gutter_bg`, `diff_sep`, etc.) to `Theme` if needed.

### Keybinding System
* Every key-driven action is one row of the registry in [src/keymap.rs](src/keymap.rs): `Action` (named `<Table><Field>`, e.g. `Action::IssuesCloseEntity`), its `KeyContext` (`Global`, `ListView`, `Tab(tab)`, `DiffView`, `Selector`, `Dialog`, `EditMenu`), its config field, its default keys, its help label (`{mr}` / `{merge_request}` / `{pipelines}` read the host's terms, and `on_github` gives a row its own GitHub label where the wording differs beyond those terms), whether it is `destructive` and which hosts it `Support`s. `Config::keybindings` is a `Keymap`: the registry defaults with every `[keybindings.<table>] <field> = "key"` (or a list of keys) from the config in their place. The table is `KeyContext::table()` (`global`, `list`, the tab's name, `diff`, `selector`, `dialog`; `submit_edit` stays under `global`).
* At runtime, every keypress is matched with `Keymap::matches(action, press)` or `Keymap::resolve(context, press)` (the first action of the context, in registry order, the key triggers), both built on `keybinding_matches(binding: &str, press: &KeyPress) -> bool` in [src/keybinding.rs](src/keybinding.rs). `parse_binding` there is the only reader of binding strings: `keybinding_matches`, `binding_key_event` (custom commands) and `KeySequences` (sequence prefixes) all go through it. Never read a binding string by hand.
* **Key sequences:** a binding is one key (a plain character, a named key such as `End`, `Return` (the same as `Enter`) or `F1` (also spelled `f1`), or a modifier combo such as `Ctrl+x`) or a sequence of two or more plain characters (`gg`, `gcc`). Named keys and modifier combos never take part in a sequence, and a binding with a space inside matches nothing. The terminal's `Event::Key` goes through `App::receive_key` into `App::key_buffer` (`KeyBuffer`), which resolves it this way: keys that start a binding wait, a complete binding nothing longer starts with fires at once, one that also starts a longer binding fires after `keybinding_timeout_ms` (`App::expire_typed_keys` on every tick, restarted by each key), and a key that completes nothing drops what was typed, a complete binding among them. The event loop takes resolved keys from `key_buffer.pop_ready()` before the channel and dispatches them as `Event::KeyPress`. An `Event::Key` taken from the channel goes to `App::receive_key` inside that same fetch, so a key is dispatched in the pass that read it instead of costing another prefetch and redraw. Keys typed into a text field (`App::is_capturing_text`) pass straight through, so add any new text-entry state there. Sequence prefixes come from every bound action (`Keymap::all_bindings`), so they wait in every context.
* Handlers take `&KeyPress`, which derefs to its `KeyEvent`. A sequence derefs to a `KeyCode::Null` event, so text-entry code that reads `key_event.code` never sees the last character of a sequence.
* **Pattern for all new action handlers:** add a registry row, then match it:
  ```rust
  _ if app.config.keybindings.matches(Action::TabAction, key_event) => { ... }
  // or
  match app.config.keybindings.resolve(KeyContext::DiffView, key_event) { Some(Action::DiffX) => ..., ... }
  ```
* Never match `KeyCode::Char('x')` (or any other literal key) for a user-facing action, not even next to the binding: remapping an action must replace its default keys, and a literal check keeps the old key alive. Only text-entry modes (the search bar, a filtering selector, the diff search, the job trace search, inline editing) read typed keys directly. The overlays the registry does not cover yet (the review threads and submit-review overlays, the configure popup, the date picker, edit-menu navigation and the help list) still match literal keys. The help modal, the custom-command shadow report and the key sequences all read the registry, so a new row shows up in each of them by itself.
* A row marked `destructive` is never dispatched by its tab arm: `handle_active_tab_key` routes it to [src/handlers/confirm.rs](src/handlers/confirm.rs), which builds the `SubmitDialog` for it, so it always asks first.

### Custom Keybindings (`[[custom_keybindings.<pane>]]`)
* User-defined shell commands bound to keys, modelled on gh-dash including its template argument names (`prs` is a serde alias of `mrs`; `normalize_custom_keybindings` renames it per file before the global and repo-local files are merged, since both keys in one merged value is a duplicate field). `Config::custom_keybindings` holds the raw entries; `App::load_keybindings()` validates them into `App::custom_commands` at startup and after the repo switcher reloads the config, logging every `ConfigProblem` as a failed Terminal-tab entry plus one toast. It logs `Keymap::problems()` the same way: a `[keybindings]` entry that names no table or action, whose value is not a key or a list of keys, or that names a key `keybinding::is_readable_binding` rejects (`"esc"`, `"Ctrl+Shift+N"`), is reported and binds nothing (the action keeps its defaults) instead of failing the whole config.
* Panes: `universal` (every tab), `issues`, `mrs`, `pipelines` (`PipelineId`, `Ref`, `Sha`), `jobs` (the Jobs tab: `JobId`, `JobName`, `Stage`, `Status`; `JobName` is `Job::api_name`, the name the API reported before `process_pipeline_jobs` split off the matrix; `Stage` is unavailable for GitHub jobs and the repository comes from `App::jobs_project`, then the job's web URL, then the repository scope, through `row_project` like issues and MRs), `branches` (`BranchName`, `CommitSha`), and `diff` (the MR/PR diff view, dispatched from the catch-all arm of `handlers::diff_view::handle_key` in [src/handlers/diff_view.rs](src/handlers/diff_view.rs); `FilePath`/`LineNumber` come from `DiffView::cursor_file_position()`). `diff_view_action()` reports the diff view's shadowed keys from `KeyContext::DiffView` plus `keymap::DIFF_VIEW_GLOBAL_ACTIONS` (the global keys that act ahead of the diff view's own actions, from the overlay chain or the diff view's handler). `custom_commands::tests::diff_shadow_report_matches_what_the_key_router_lets_through` sends every global and diff default key through `update` with a `[[diff]]` command on it and fails when the router and `diff_view_action()` disagree, so a key handled before the diff view must be added to that list. Template arguments per pane live in `CommandPane::template_arguments()`; row values are resolved in [src/handlers/custom_commands.rs](src/handlers/custom_commands.rs) from the highlighted row. `RepoPath` is `git_helpers::repo_root()` in repository scope and `cache::find_local_checkout()` (recent repos by `origin`) in group scope.
* Dispatch happens in the last arm of the list-view fallback in `handle_active_tab_key`, so every built-in wins. `builtin_action()` in [src/custom_commands.rs](src/custom_commands.rs) asks the registry (`Keymap::resolve` over `KeyContext::Global`, the tab's context and `KeyContext::ListView`) which action takes a key, so a key added to the registry is reported without touching the shadow detector. Pane-specific custom bindings win over universal ones.
* A non-empty `selected_issues` / `selected_mrs` / `selected_pipelines` / `selected_jobs` / `selected_branches` turns an `issues` / `mrs` / `pipelines` / `jobs` / `branches` command into a bulk run: `targets()` yields one `Target` per selected item (sorted by project and number, jobs by id, branches by name), and all renderable runs execute inside one `editor::suspend_while` handoff. `run_all` times each run (`FinishedRun::execution`: start time and duration), and each run is logged with that timing through `App::record_command_outcome` (terminal runs) or `App::settle_command` (background runs); failures raise a single summary toast via `App::raise_error_toast`.
* `background = true` entries skip the handoff: `execute()` runs them on a thread with stdin/stdout detached (`Handoff::Background`) and sends `Event::CustomCommandFinished(RunReport)`; the main loop logs it through `report_runs()`, the same path terminal runs use. Stderr is always collected so a failure names its cause; it is only echoed to the screen for terminal runs. `detach_from_terminal()` starts background runs with `setsid(2)` (Unix): Go/termenv tools open `/dev/tty` and query the background colour even with stdio redirected, and the terminal's reply would otherwise arrive as keypresses. `tests/e2e/custom_keybindings.rs` guards this.
* Feedback while a command works: a background run logs each rendered command as `Running` up front (`App::start_command`) and `report_runs()` settles those rows through their `LogRow` handles (`RunReport::log_rows`, `App::settle_command`); a terminal run prints `glab-tui: running "<label>": <command>` to stderr before starting, so a silent command does not leave a blank screen. Custom-command log rows start with `CUSTOM_COMMAND_LOG_PREFIX` (Terminal-tab re-runs with `RERUN_LOG_PREFIX`, review submissions with `REVIEW_SUBMIT_LOG_PREFIX`), and the generic "most recent `Running` entry" fallbacks (`show_error`, `CommandCompleted`, `TerminalCommandLogged`) go through `App::latest_running_cli_command()`, which skips them so an unrelated completion cannot stamp a background command finished.
* `render()` splices a value into `sh -c` only when it is a single plain word: it refuses values starting with `-` or `+` (vim/nvim/less run `+cmd` as a command, and `FilePath` comes from the PR diff) and values containing whitespace, control characters or a `SHELL_SIGNIFICANT_CHARACTERS` entry (quoting, substitution, separators, redirection, glob, brace/tilde expansion, `#`, `=`). Every value is also exported as `GLAB_TUI_<NAME>`, the only safe way to pass free text such as titles. Keep that guard when adding arguments.
* Keys are parsed with `keybinding::binding_key_event`, the inverse of `keybinding_matches`; a key it rejects is reported as unbindable.

### Submit Dialog & Confirmations (`SubmitDialog`)
* Mutating and destructive actions (close/reopen issue/MR, merge MR, bulk merge, delete branch/release/milestone/issue/MR, rebase, revoke approval, submit review, cancel pipeline, bulk job cancel, stop environment, roll back deployment, re-run of a Terminal-tab command) open a `SubmitDialog` ([src/app.rs](src/app.rs)). Confirmed bulk job cancels are paced with `pace_bulk_operation()`.
* Pipeline and job actions resolve their project through `App::project_path_for_pipeline(id)` (the listed row's `project_path`, then `active_pipeline_project` for the active pipeline, then the scope) or `App::project_path_for_jobs()` for the Jobs tab. `App::pipeline_project(id)` / `App::jobs_project()` are the same lookups without the scope fallback, and `active_pipeline_project` only ever holds what `pipeline_project` resolved, never the scope. Never pass `app.scope.as_str()` as a pipeline/job project: in group scope it is the group path.
* `SubmitDialog` is an `action`, a `project_path`, its `extra_buttons` (`DialogChoice`, between Submit and Cancel; the submit-review dialog uses them for `Keep drafts` / `Discard`), the `strategies` its `Strategy` radio offers (in the radio's order, so the selected index maps back to a `MergeMethod`) and a `Form` built by `SubmitDialog::build_with_project`: the body text as an `Info` note, then the action's groups (merge and bulk merge: the `Strategy` radio over `strategies` (every `MergeMethod::ALL` today) and the `Options` toggles, bulk merge also listing its items. Stack merge: its PRs and the `Strategy` radio, since its handler reads only the method. Bulk branch delete: its branches as an `ItemList`, so a cut list ends in `N more`), then the buttons Submit, the extras, Cancel. `handle_submit_dialog` / `click_submit_dialog` forward keys and clicks to the form and carry out its `FormAction`. A merge reads its choices through `SubmitDialog::merge_choices()` (`MergeChoices::options(sha)` builds the `MergeOptions`), never from labels.
* Keys are the form's: `Tab`/`BackTab` between groups (the button row last, entered on Cancel, and across the buttons in a form without groups to focus), `j`/`k` within a group and on into the next (past the last group onto Cancel), `h`/`l` across radios and buttons, `Space` or `Enter` selects or toggles the focused option, `Enter` on a button runs it and from a line input runs the primary one, `Esc` leaves a line input being edited, then cancels. Cancel never has side effects, so moving the focus never arms the action.
* Actions where `ConfirmAction::is_destructive()` holds (close, reopen, delete, revoke, mark all todos read, cancel pipeline/jobs, stop environment, roll back deployment) open with `Form::danger()`, which puts the focus and the primary on Cancel. Merge, rebase, review and re-runs (the user asked for that exact call, shown in full in the body) open on Submit.
* Clicks on rows and buttons go through `Form::click_at`, using the rects the last draw recorded.
* E2E coverage: `tests/e2e/merge_dialog.rs` picks a strategy and options in the merge dialog with the form's keys and asserts the exact `glab mr merge` / `gh pr merge` call they produce (the `mr merge` and `pr merge` cases of `tests/mocks/glab` and `tests/mocks/gh`). Destructive dialogs are driven from Cancel by `tests/e2e/group_scope_actions.rs`, `secondary_tabs.rs` and `tabs.rs`.

* All modal and overlay interactions (submit dialogs, selectors, date picker, help) have click handlers routed through their respective state components.

### Column Configure Popup
* The configure overlay (`Tab`) has three sections: **COLUMNS** (checkbox toggle), **GROUP BY** (single-select), and **ORDER** (Ascending/Descending).
* Column lists use `ListState` scrolling with position counters to handle short terminals gracefully.
* Value-based column filtering is available by pressing `Enter` on a focused column item, which opens a selector overlay with distinct values for that column.
* Column filter state is tracked via `app.column_filter_context` and `app.column_filters: HashMap<Tab, HashMap<String, Vec<String>>>`.
* Group state is tracked via `app.group_by_column: Option<String>` and `app.group_ascending: bool`.
* **State filter → server state (GitHub repositories only):** the Issues and MRs/PRs State filter picks what `gh issue list` / `gh pr list` fetch. `App::state_filter_query` turns one selected state into a `StateQuery` ([src/domain/state_query.rs](src/domain/state_query.rs)). Two or more states, or no filter, give `All`. `Backend::server_state_query` decides what the server is asked for: GitHub narrows repository listings, while GitLab and GitHub org listings keep fetching every state. Every `spawn_refresh_active_tab` / `spawn_refresh_all_tabs` call passes `app.requested_state_queries()`. `IssuesFetched` / `MrsFetched` carry the query they were listed with. A result that does not cover the current filter is dropped, and `ProjectCache::issues_state_query` / `mrs_state_query` make `App::restore_cached_issues` / `restore_cached_mrs` skip cached rows listed for a narrower state. `fetch::dispatch_state_query_refetch` (on `Event::Tick`) refetches a loaded or loading tab once its requested query changes, whatever path edited the filter. While the server narrows, the State picker offers every state, so the user can switch to one that was not fetched.
* When rendering the MR/PR pipeline status column, check `is_github` to display "Pipeline" (GitLab) or "Action" (GitHub) terminology.
* MR/PR review-state columns (`Approval`, `Mergeable`, `Workflow`) are derived in [src/domain/mr_state.rs](src/domain/mr_state.rs).

## 4. UI & Rendering Guidelines (`ratatui`)

* **Colors, icons & `RenderCtx`:** `ui::render` builds one `RenderCtx` ([src/ui/render_ctx.rs](src/ui/render_ctx.rs)) per frame from `App` (`theme: Theme` copied from `App::theme`, `icons: &Icons` from a clone of the `App::icons` `Arc` so it can sit beside `&mut App`, and `kind: BackendKind`) and passes it as `ctx: &RenderCtx<'_>` right after `f: &mut Frame` to every render function. Read colors as `ctx.theme`, glyphs as `ctx.icons`, the host as `ctx.kind`, and the shared table styles as `ctx.header_style()` / `ctx.highlight_style()`. There is no global theme or icon set: leaf helpers that only need colors take `theme: &Theme` (see `render_markdown`, `render_fuzzy_cell`), ones that only need glyphs take `icons: &Icons`. Tests render with `RenderCtx::new(&app, &icons)` or, without an `App`, `RenderCtx::for_tests()`. Do not hard-code raw RGB values; add new semantic color tokens to `src/config.rs` and all theme TOML files if needed. Every surface is theme-driven, including the diff view (`diff_addition_*`/`diff_deletion_*`/`diff_gutter_bg`/`diff_sep`/`comment_bg`/`comment_draft_bg`), markdown rendering, and diff selection/search-match highlights (`highlight_bg`/`yellow_bg`).
* **Fuzzy Matching:** Use `SkimMatcherV2` from the `fuzzy-matcher` crate for filtering tables and selector overlays. The `render_fuzzy_cell` helper in [src/ui/helpers.rs](src/ui/helpers.rs) handles highlighting matched characters in yellow.
* **Untrusted Text:** Titles, descriptions, comments, release notes and job/stage names come from third parties and may carry raw ANSI escape sequences. Pass them through `sanitize_untrusted()` ([src/utils/format.rs](src/utils/format.rs)) before building spans; it strips CSI/OSC/DCS sequences (7-bit and C1) and stray control characters, and borrows the input unchanged when it is clean. `render_markdown`, `render_fuzzy_cell`, `format_comment_with_suggestions` and the inspector field list already do so; `strip_ansi_escapes()` is the owned-`String` form used by the diff parser and job-trace wrapping.
* **Columns:** Table columns are dynamically configurable. `ListTab` tabs draw only the columns enabled in `app.enabled_columns`, which `sync_list_views` feeds into the view, so `ListTab::render` needs no per-cell check. `StatefulTable` tabs must check `app.is_column_visible(tab, "Column Name")` before rendering each cell and header. GitHub-only or GitLab-only columns must also gate on `app.gitlab_client.is_some()` / `is_github`.
* **Layout:** Use `ratatui::layout::Layout` to split screens. Avoid hardcoded fixed sizes where possible, use `Constraint::Percentage` or `Constraint::Fill(1)`. Use `centered_rect_min()` for overlays to ensure minimum readable dimensions on small terminals.
* **Compaction:** New layouts that adapt to the terminal size go through `ui::compaction::compact` ([src/ui/compaction.rs](src/ui/compaction.rs)): the screen lists the steps it can give up, most expendable first, and they are applied in order until its `fits` check passes (the last one applies when nothing fits). Do not add a bare width threshold. The workspace (`place_preview`, used by `Workspace::split` in [src/ui/mod.rs](src/ui/mod.rs)) keeps the preview beside the list at the width `preview_columns` asks for while the list keeps `MIN_LIST_COLUMNS`, then narrows it to `MIN_PREVIEW_COLUMNS`, then stacks it below the list, then gives up the terminal log under them, then hides the preview once either pane would get fewer than `MIN_STACKED_PANE_ROWS` rows. The placement is measured on the width the configured sidebar leaves, so leaving the sidebar out under `MIN_SIDEBAR_TERMINAL_COLUMNS` never moves the preview. `preview_columns` only picks the preferred width, never the placement. The diff view (`fits_side_by_side_diff`) goes unified below two `MIN_SIDE_BY_SIDE_PANE_COLUMNS` panes and the `SIDE_BY_SIDE_DIVIDER_COLUMNS` divider between them. The sidebar's 80-column cutoff, the terminal log's 18-row cutoff and `col_w`'s column-width tiers predate it and are not rules yet.

## 5. Adding a New Feature (Workflow)

If asked to add a new Tab (e.g., "Deployments"):
1.  **Update State:** Add the tab to the `Tab` enum in [src/app.rs](src/app.rs) (include it in `ALL`, `title()`, `columns()`, and `default_columns()`). Add a `ListTab<YourColumn>` to `App` with a `ColumnDef` enum in [src/ui/list_tab/](src/ui/list_tab/), and add it to `sync_list_views` / `list_navigation(_mut)`.
2.  **Define Domain Logic:** Create [src/domain/deployments.rs](src/domain/deployments.rs). Define the `Deployment` struct with `serde` traits. Write a `list_deployments` function that delegates to the backend.
3.  **Add Backend Methods:** Add the relevant method to the `Backend` trait in [src/backend/mod.rs](src/backend/mod.rs) and implement it in both [glab.rs](src/backend/glab.rs) and [gh.rs](src/backend/gh.rs). Use native subcommands where available; fall back to `raw_api()` only if no native command exists.
4.  **Create Events:** Add `DeploymentsFetched(Vec<Deployment>)` to the `Event` enum in [src/event.rs](src/event.rs).
5.  **Handle Data Fetching:** Update `refresh_tab` in [src/fetch.rs](src/fetch.rs) to fetch data for the new tab.
6.  **Handle UI Updates:** In `events::apply` ([src/update/events.rs](src/update/events.rs)), handle `Event::DeploymentsFetched` with `app.deployments.set_items(..)`, call `app.update_filter_selection()`, copy `app.deployments.items()` into `app.project_cache` and save the cache.
7.  **Handle Navigation:** In [src/handlers/tabs.rs](src/handlers/tabs.rs), add the tab to the `Runners | Releases | Branches | Environments` arms of the `KeyCode::Down`/`Up`/`Home`/`End` handlers, which move the cursor through `app.list_navigation_mut(app.active_tab)`. Mouse scroll and click already go through `list_navigation_mut`.
8.  **Render:** In [src/ui/tabs.rs](src/ui/tabs.rs), add a `render_tab_deployments` that calls `app.deployments.render(f, area, TableContext { .. })` and builds the details preview from `app.deployments.cursor_row()` with `render_list_preview`.

## 7. Development & Quality Standards

* **Error Handling:** Use `anyhow::Result`. Bubble up errors and display them in the UI via `App::show_error(msg)`. Do not `unwrap()` or `panic!()` in UI or event handling code.
* **Test env isolation:** Unit tests that mutate process-global environment variables (config paths via `GLAB_TUI_CONFIG`/`XDG_CONFIG_HOME`, cache dirs) must acquire `config::TEST_ENV_MUTEX` first (`config::lock_test_env()`, which also takes it after another test panicked holding it) — env vars are visible to every test thread, and overlapping mutations caused an intermittent Windows CI failure. Never introduce a second ad-hoc mutex for env mutation; reuse the crate-wide one. `App::default()` starts from `Config::default()` and reads no config file, and unit tests see only the bundled themes, so tests build their `App` with it; `App::new()` and `Config::load()` read the developer's global and repo-local config, so a test that calls them isolates the config first with `config::isolate_config()`: the mutex, a temporary home (`HOME`, `USERPROFILE`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME`, with `GLAB_TUI_CONFIG` unset) and that home as working directory, so no repo-local config is found either. Outside `config.rs`, a test changes the working directory only through `isolate_config()`.
* **Secondary-tab smoke matrix:** `tests/e2e/secondary_tabs.rs` drives Runners, Releases, Todos, Milestones, Branches and Environments on GitLab: list every fixture row, filter to one with `/`, run one action on it. The `glab` mock serves `runner list` / `release list` / `todo list` / `milestone list` and the branches / environments / deployments endpoints from `tests/fixtures/{runners,releases,todos,milestones,branches,environments,deployments}.json`. Every list fixture holds two rows so a search visibly narrows the list. `TestSession::press_keys` sends keys one at a time and `TestSession::wait_for_cli_call` waits for a mocked call.
* **Unknown mock calls fail the test:** a `gh`/`glab` call the mocks in `tests/mocks/` have no case for exits 2 and is appended to `<TEST_LOG_PATH>.unhandled`. `Sandbox::drop` (`tests/e2e/main.rs`) fails the test while that file is not empty and lists the calls, after waiting for mocks still running once the app was killed. A new call glab-tui makes needs a mock case. Injected failures (`TEST_*_FAIL_*`) exit 1 and are not recorded.
* **Overlay snapshots:** `ui::overlays::tests` renders the merge `SubmitDialog` at 60, 80 and 120 columns and a twenty-item bulk merge (which exercises the form's compaction) at 60 and 80 columns on a `TestBackend` and compares them with `src/ui/snapshots/*.txt` (icons normalized to the ASCII set, so the developer's icon config cannot change the result). After an intended layout change, regenerate with `GLAB_TUI_UPDATE_SNAPSHOTS=1 cargo test --lib merge` and review the diff.
* **Dependencies:** Do not add large dependencies (like `reqwest` or `hyper`) for HTTP API calls. The architecture strictly dictates delegating HTTP requests to `gh` and `glab` CLI binaries via `tokio::process::Command` in `GitlabClient`.
* **Before a change is done:** run `just check`. It runs the recipes that CI's Rustfmt, Clippy and Test jobs run: `fmt-check` (`just fmt` fixes it), `lint` (Clippy over all targets with warnings denied), `test` (unit tests) and `e2e` (needs `cargo-nextest`). The Justfile is the source of truth for these commands.
* **Tests:** Unit tests live in the library, and `just test` covers them. `cargo test --bin glab-tui` alone only covers the tests in `main.rs`.
* **Bug fixes start with a test:** a bug fix starts with a test that fails without the fix, in the same PR.
* **MSRV:** The Minimum Supported Rust Version is `1.88`. Edition 2024
  requires Rust 1.85+, but current transitive dependencies raise the floor
  to 1.88 (see `.github/workflows/msrv.yml`). Ensure code is compatible.

## 8. Release Process (Local-First)

Releases are prepared, documented, and distributed from a maintainer's machine via a single orchestrator, `scripts/release.sh`. CI is only responsible for building the cross-platform release binaries. The demo GIFs must be recorded locally because `glab-tui` shells out to `gh`/`glab`, and CI tokens lack the permissions for a realistic recording.

Run `scripts/release.sh [patch|minor|major|nightly]` (default `patch`) and the script walks the full release:

> **Nightly Pre-Releases:** `scripts/release.sh nightly` (or tags matching `vX.Y.Z-nightly[-suffix]`) runs a stripped-down flow that skips `Cargo.toml` bumping, docs regeneration, prepare PRs, demo GIFs, review gates, Homebrew/Scoop manifest syncs, and crates.io publishing, while still building matrix binaries and updating GitHub release notes.

1. **Preflight** — checks `gh`/`opencode`/`cargo`/`jq`/`vhs`/`ttyd`/`ffmpeg`/`unzip`, `gh auth`, JetBrainsMono Nerd Font, and push access to both manifest repos (`rcieri/homebrew-glab-tui`, `rcieri/scoop-glab-tui`); exits non-zero with a clear message if a prerequisite is missing. Long-running steps run under the script's `spinner`/`progress_bar` helpers (animated spinner with captured logs, auto-disabled when not a TTY), and phases are numbered `1/7` … for progress reporting.
2. **Prepare** — computes the next tag from `git describe --tags`, bumps the crate version in `Cargo.toml`, prompts for the AI tool (`agy` or `opencode`) and model unless configured via `AI_TOOL`, `AGY_MODEL`, or `OPENCODE_MODEL`, regenerates `CHANGELOG.md`/`README.md` via the selected AI tool, rebuilds the demo GIFs against an authenticated `gh`, and opens a `chore: prepare release vX.Y.Z` PR.
3. **Review gate** — pauses for the maintainer to review the PR (CI checks run in the background); the script continues on Enter.
4. **Merge & tag** — squash-merges the PR with `--auto`, tags the merge commit and pushes `vX.Y.Z`. `.github/workflows/release.yml` builds the 11-target binary matrix (8 Linux + 3 non-Linux) and uploads them to the GitHub release.
5. **Wait for build** — polls the release until every required asset exists (timeout: `RELEASE_WAIT_MIN`, default 45 min). The required-asset list in `REQUIRED_ASSETS_STATIC` covers the fixed name patterns; the dynamic Ubuntu-latest build is required to produce at least two `ubuntu-<VERSION_ID>` assets whose VERSION_ID differs from the 22.04 / 24.04 baselines. The script protects against unbound variables and off-by-one asset-count math under `set -u`, and it can resume from a chosen phase (`--phase`) if an earlier step failed or was interrupted.
6. **Post-release** — generates `RELEASE_NOTES.md` via the selected AI tool (entries attribute their contributors as `(thanks @username)` and a `**Contributors**` section lists all `@username` handles since the previous tag), and updates the release body on GitHub.
7. **Publish** — pushes the Homebrew formula (`rcieri/homebrew-glab-tui`), Scoop manifest (`rcieri/scoop-glab-tui`), Docker image to GHCR, and publishes the crate to crates.io (skipped for nightly).

### Release Assets

`.github/workflows/release.yml` builds an 11-entry matrix (8 Linux + 3 non-Linux) on every `v*` tag push. **Linux builds target a glibc 2.35 baseline (Ubuntu 22.04) for backwards compatibility with older distros, plus per-LTS and `ubuntu-latest` variants for current distros, and a fully static musl fallback for non-glibc systems.** The `ubuntu-latest` runner's `VERSION_ID` is detected at build time and baked into the asset name (e.g. `glab-tui-linux-amd64-ubuntu-26.04.tar.gz` when `ubuntu-latest` resolves to Ubuntu 26.04), so the asset set adapts to future LTS releases without code changes.

Asset name pattern:

| OS | Arch | Asset name | Built on |
|---|---|---|---|
| Linux | x86_64 | `glab-tui-linux-amd64-ubuntu-22.04.tar.gz` | `ubuntu-22.04` runner (glibc 2.35 baseline) |
| Linux | x86_64 | `glab-tui-linux-amd64-ubuntu-24.04.tar.gz` | `ubuntu-24.04` runner (glibc 2.39) |
| Linux | x86_64 | `glab-tui-linux-amd64-ubuntu-<VERSION_ID>.tar.gz` | `ubuntu-latest` runner (current LTS) |
| Linux | aarch64 | `glab-tui-linux-arm64-ubuntu-{22.04,24.04,<VERSION_ID>}.tar.gz` | cross-compiled from `ubuntu-{22.04,24.04,latest}` x86_64 runners |
| Linux | x86_64 / aarch64 | `glab-tui-linux-{amd64,arm64}-musl.tar.gz` | `ubuntu-22.04` (static, no glibc dependency) |
| macOS | x86_64 / arm64 | `glab-tui-macos-{amd64,arm64}.tar.gz` | `macos-latest` |
| Windows | x86_64 | `glab-tui-windows-amd64.zip` | `windows-latest` |

The asset-suffix table in `release.yml` is the single source of truth — `linux_variant: ubuntu-latest` causes the build step to read `/etc/os-release` and bake `VERSION_ID` into the asset name.

#### Asset selection logic

Three places pick the right asset for the running host:

- **`install.sh`** (`linux_asset_candidates`) — builds a candidate list from `/etc/os-release`. On Ubuntu it tries the local version first, then walks down through `ubuntu-24.04` → `ubuntu-22.04`, then falls back to `musl`. Non-Ubuntu Linux distros try `ubuntu-22.04` → `ubuntu-24.04` → `musl` directly. Override with `GLAB_TUI_ASSET=glab-tui-linux-amd64-musl.tar.gz` for testing.
- **`src/utils/update.rs`** (`linux_asset_candidates`) — mirrors `install.sh` for the in-app self-updater; queries the GitHub release's asset list through `curl` and picks the first match.
- **Homebrew formula** (`update_homebrew` in `release.sh`) — pins the fully static musl builds for Linux (x86_64 and arm64), which run on any Linux distro regardless of glibc version, and native macOS binaries.

Every install path verifies the downloaded archive against the release's `<asset>.sha256` (generated by `release.yml`) before extracting it, and refuses to install when the checksum asset is missing or does not match: `install.sh` (`verify_checksum`, via `sha256sum` or `shasum`), `install.ps1` (`Get-FileHash`) and the self-updater (`verify_archive_checksum`). Checksum lines are `<hex>  <name>`, or `<hex> *<name>` for the Windows zip.

Scoop's manifest (`rcieri/scoop-glab-tui`) is unaffected — Windows keeps the fixed `glab-tui-windows-amd64.zip` name.

During `Prepare` and `Post-release`, `release.sh` prompts to select the AI tool (`agy` or `opencode`) and model for the regenerated `CHANGELOG.md`/`README.md` and release notes; set `AI_TOOL` and `AGY_MODEL` / `OPENCODE_MODEL` to skip prompts.
